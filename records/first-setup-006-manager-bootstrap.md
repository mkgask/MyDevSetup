### Entry 0001 (2026-10-24)
- Why now: The user wants to consider installing proto and mise during `first-setup.sh` because `dev-tools.sh` uses them as development-tool installation managers.
- Findings / trade-offs:
  - Current `first-setup.sh` is a root-level, manual OS bootstrap run before `install.sh`; it installs apt dependencies and user-local HackGen fonts. Active decision `installer-011-22-6-side-effect-boundary` explicitly excludes installing tools and changing shell startup files, PATH, or manager settings.
  - `dev-tools.sh` only offers proto/mise routes when the manager already exists and can identify a supported tool. Its active backend contract says it does not install a missing manager or plugin. Proto is preferred when supported; mise is a later fallback. Installing both during first setup will therefore change the routes and default choices shown by a subsequent `dev-tools.sh` run.
  - After a user selects a proto/mise route to install an actual tool, `dev-tools.sh` already activates the chosen manager in its current process and appends its Bash activation line to `~/.bashrc` once. First setup would need to make the manager executable discoverable before that route probe, but activating both managers globally during bootstrap is not necessary for this flow and could change all future shell environments.
  - The official proto install guide targets `~/.proto`, supports `--yes` and `--no-profile`, and lists `git`, `tar`, `unzip`, `gzip`, and `xz` as requirements. The current apt list includes all except `tar`. Proto's Bash activation can add its bin/shim paths to PATH.
  - The official mise installer places the executable at `~/.local/bin/mise`; that location is not on PATH on every system. The Bash-specific installer endpoint adds activation to `~/.bashrc`, while the generic installer only installs the binary. Its activation guidance requires the executable to be reachable when the startup file runs.
  - Because `first-setup.sh` is commonly run as `curl | bash`, it cannot export PATH changes back to the interactive shell that launched the pipeline. If it adds manager paths to the profile, the user must source that profile or start a new shell before running `install.sh`; otherwise `dev-tools.sh` may not detect the newly installed managers. `install.sh` itself runs `dev-tools.sh` in a child Bash process.
  - Both upstream installers add network-delivered executable code and install user-scoped manager binaries. The first-setup script is documented for normal-user execution, but currently permits root execution; installing into `/root` would not prepare the invoking user's environment. Existing manager installs should not be silently upgraded as part of an idempotent bootstrap.
- Focus areas:
  - Whether the no-argument bootstrap should install both missing managers by default or make manager setup opt-in.
  - Whether first setup should modify Bash startup configuration to expose `~/.proto/bin` and `~/.local/bin`, and how the README makes the new shell/source step explicit before `install.sh`.
  - A user-scope, non-interactive, idempotent install contract that skips existing managers, reports upstream install failures, and leaves language tool/version/plugin installation to `dev-tools.sh`.
  - Whether manager installation should fail when invoked as root, given that apt currently supports root while manager binaries and fonts are user-scoped.
- Explicit exclusions: Do not install Python, Ruby, Node.js, or other language tools from `first-setup.sh`; do not add manager installation to `dev-tools.sh` install/status/dry-run; do not alter manager route mappings or proto/mise post-install activation; do not add other managers or non-apt operating systems in this discussion.
- Current conclusion: Preliminary recommendation is for no-argument `first-setup.sh` to install both proto and mise only when missing, after apt dependencies, as the current user. It should install manager binaries only (not tool runtimes, plugins, or versions), ensure their command paths are available to `dev-tools.sh`, and preserve the latter's existing activation behavior after a manager route is selected. Since the script runs in a child process, profile changes would require a clear `source ~/.bashrc` or new-shell step before `install.sh`. Whether these manager installs should be default or opt-in, and the exact profile/root policy, remain unconfirmed; no active decision has been changed.
- Next validation target: Discussion-validation should check whether default installation of both managers is justified by the changed `dev-tools.sh` route selection, whether PATH-only setup is sufficient without globally activating both managers, whether adding `tar` is required by the official proto installer, and how root invocation and the extra remote-installer trust boundary should be handled. It should then name the precise first-setup side-effect, lifecycle, output/header, README, and test contracts to update before implementation.
- Promotion to DECISIONS.yml: pending user direction
